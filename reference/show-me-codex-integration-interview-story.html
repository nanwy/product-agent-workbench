Interview explainer · Codex integration

从“能跑”到“能实时、能恢复”

这段经历真正有分量的地方，不是换了 CLI、SDK 和 app-server，而是我先确认事件的真实粒度，再把合批和一致性的责任放回正确的一层。

一句话结论

我把“流式”拆成事件流、文字增量、传输合批和断线恢复四个问题，逐个验证，不再用一个模糊的 streaming 概念解释全部现象。

方案为什么改了三次

1 先跑起来

Node 读取 CLI stdout

逐行解析 codex exec --json 的 JSONL，工具和完成事件可以及时到达。

问题：stdout 在流动，不代表 assistant 正文也在增量输出。正文经常到完成事件才整段出现。

2 减少自维护协议

接入 TypeScript SDK

Thread 恢复、取消和结构化事件都更好管理。我原本判断 SDK 能顺手解决正文流式。

验证：抓原始事件后发现，当时的版本组合仍主要在 item 完成时给正文。事件流和文字流不是一回事。

3 换协议能力

切到 Codex app-server

消费 item/agentMessage/delta，终于能按上游实际粒度更新同一条 assistant 消息。

新问题：小片段直接推给浏览器会造成高频传输和缓存更新；断线还可能留下不完整文本。

4 重画责任边界

合并机制下沉后端

服务端按时间或字节数合成 SSE 批次，同时周期性保存累计全文。前端只负责按消息 ID 投影。

结果：页面保持跟手；序号缺口时可回到持久快照；完成事件再校准最终全文。

最值得讲的判断

早期判断

前端用 Zustand + requestAnimationFrame 缓冲，能少做几次渲染，所以把“流式性能”留在浏览器处理。

→

后来判断

RAF 只减少浏览器提交次数，不能减少网络事件，也无法为多个客户端提供统一顺序和恢复点。合批属于传输边界，应由后端负责。

问题拆解

把“SDK 能不能 streaming”拆成事件是否连续、正文是否有 delta、前端是否平滑、断线后是否一致。

证据意识

直接看原始 JSONL 和事件类型，不靠方法名 runStreamed() 猜能力，也不把模拟数据当成真实协议。

架构取舍

CLI 适合快速验证，SDK 适合封装会话，app-server 提供所需正文增量；选择跟需求走。

边界设计

后端合批和持久化，React Query 做客户端投影，最终全文按 item ID 覆盖，避免重复追加。

STAR 骨架

S

项目要把 Codex 接进 Web 工作台，用户需要在 Agent 执行时持续看到回复，而不是任务结束后突然出现整段内容。

T

我负责打通 Codex 到页面的消息链路，同时保证刷新或断线后不会丢字、重字。

A

我先后验证 CLI stdout 和 SDK 的真实事件，确认当时组合缺的是正文 delta；随后切到 app-server。拿到 delta 后，我又把前端 RAF 合并改成服务端按阈值合批，并补上序号检测、快照恢复和最终全文校准。

R

最终页面能按上游实际粒度渐进显示，断线时也有恢复路径。更重要的是，实时性、传输成本和数据一致性有了清晰的责任边界。

面试口述稿，约 90 秒

自然表达版 · 不编造指标 · 可直接练习

“这个项目里比较难的一段，是把 Codex 的输出做成真正可用的实时对话。

第一版我在 Node 里启动 codex exec --json，逐行解析 stdout。工具开始、命令完成这些事件确实会不断到，但 assistant 正文经常等到 item.completed 才整段返回。后来我接了官方 TypeScript SDK，主要是想把 Thread 恢复和取消交给官方封装。我当时以为 runStreamed() 也能解决正文流式，结果抓了原始事件才确认：在我们当时测试的版本组合里，流动的是生命周期事件，正文还没有可用的增量。

所以我没有继续在前端做假打字效果，而是把默认通道换成 Codex app-server，消费它的文字 delta。接通以后又碰到第二个问题：每个小片段都推到浏览器，会产生很密的 SSE 和缓存更新；一旦断线，页面还可能少一截。早期我们在前端用 Zustand 和 RAF 合并渲染，后来我把这个机制移到后端。服务端按时间或字节阈值合成批次，同时保存累计全文；前端用 React Query 按消息 ID 投影，发现序号缺口就重新取快照，最后再用完成事件的全文校准。

最后解决的不只是‘让字一点点出来’，而是让实时显示、传输成本和恢复一致性能够同时成立。这个过程也让我意识到，看到 streaming 这个方法名还不够，必须看协议里到底流的是什么。”

讲完以后，面试官会怎么追

通常不会一上来问代码细节。面试官会先确认你的判断有没有证据，再看架构取舍，最后追异常场景和复盘。每个回答控制在 20 到 40 秒，答完停一下。

  1. 先证伪
  2. 再问取舍
  3. 压异常场景
  4. 看度量与复盘

1先确认：你真的定位到根因了吗

SDK 不是支持 streaming 吗？为什么说做不了流式？

我不会说 SDK 做不了流式。它支持结构化事件流。问题是我们当时测试的版本组合里，assistant 正文主要在 item.completed 才完整出现，没有拿到能直接用于逐步渲染的正文 delta。我最后换协议，是因为页面需要的是文字增量，不是单纯知道任务还在执行。

你怎么确认不是前端渲染慢，或者 Node 读取 stdout 有问题？

我绕过页面，直接保存原始 JSONL。工具开始和完成事件会连续到达，但 assistant 文本集中在同一个完成事件里。换 SDK 后我又记录了一次原始事件，现象一致。这样就把问题定位到了上游事件粒度，而不是 React 渲染或 stdout 分块。

为什么不用前端模拟打字，用户看起来也一样？

模拟打字只能改善动画，不能改善真实等待。如果正文十秒后才整段到，前十秒用户还是看不到内容；而且动画会让监控看起来像“正在接收”，实际只是重放已有文本。我更希望页面反映真实状态，所以继续找有正文 delta 的协议。

从 CLI 换 SDK，那次改造是不是白做了？

不是，SDK 解决了另一类问题。Thread 恢复、取消、沙箱参数和事件类型不再由我们手写维护。它没有满足当时的正文增量需求，但帮我把“会话控制”和“文字流式”分开了。后面切 app-server 时，需求边界反而更清楚。

2继续追：为什么这样划分前后端职责

为什么最后选 app-server，而不是继续解析 CLI？

因为 app-server 提供了我缺少的协议语义。CLI JSONL 更适合快速集成和观察任务事件，app-server 有明确的 item/agentMessage/delta，还能把 Thread、Turn 和 item 关联起来。代价是接入更复杂，所以我保留了 Adapter，把协议差异隔离在服务端。

为什么把 RAF 合并从前端移到后端？

因为 RAF 只省浏览器渲染，不省传输。每个小片段仍会经过 SSE、事件解析和缓存更新；开两个页面还会各自做一遍。服务端合批后，所有客户端拿到统一的批次和序号，前端只做投影，恢复逻辑也只有一套。

为什么前端从 Zustand 换成 React Query？

这部分状态本质上来自服务端。它有快照、失效、重取和断线校准，React Query 对这套生命周期更顺手。Zustand 仍适合纯本地交互状态，但如果让它同时保存服务端真相和临时增量，很容易出现两份状态谁覆盖谁的问题。

50ms、4KB 这些阈值是怎么定的？

它们是可调的工程参数，不是拍成永远正确的常量。时间阈值保证低速输出时页面不会等太久，字节阈值防止高速输出时单批过大。初值先保证体感和内存可控，再根据首批延迟、每秒事件数和批次大小分布调整。

3再压一层：异常和一致性怎么处理

SSE 断线重连，不就能继续接收了吗？

重连只恢复连接，不代表中间没有漏事件。我给批次带连续序号。前端发现序号跳了，就停止相信本地拼接结果，重新拉持久化快照；连接恢复后再继续投影新的批次。这里做的是发现缺口后的校准，不是假设 SSE 会替我补历史消息。

delta 重复到达，或者 completed 又带了一遍全文，会不会重复？

不会把 completed 当成新的文本继续追加。增量按 Turn 内的 item ID 累积，旧序号直接忽略；完成事件到来后，用同一个 item ID 的最终全文覆盖临时拼接结果。这样即使中间有重复或少量缺失，最终状态也会收敛。

多个 Turn 同时输出，顺序怎么保证？

顺序只在明确的作用域里保证。批次至少带 Turn ID、item ID 和序号，前端按 Turn 分开记录最后序号，不拿一个全局计数器混在一起。同一 item 内顺序合并，不同 item 不跨边界拼接；跨 Turn 的展示顺序由会话时间线决定。

服务端一直缓存累计文本，会不会占用很多内存？

内存只保存活跃 Turn 的短期缓冲。达到时间或字节阈值就 flush，完成、取消和异常时都会清理；较长内容周期性落到持久快照，不把完整历史都留在合批器里。真要上更大并发，我还会加单 Turn 上限和活跃会话指标。

4最后看：你怎么证明效果、又学到了什么

你怎么衡量改造有效？

我会分体验、开销和正确性三组看。体验看首段正文时间和批次间隔；开销看每个 Turn 的 SSE 事件数、平均批次大小和前端缓存更新次数；正确性看序号缺口、快照回退次数，以及最终全文和持久结果是否一致。当前没有可靠数字的部分，我不会在面试里临时编。

如果 app-server 挂了，系统怎么降级？

我会保留协议 Adapter 和明确的降级能力。可以退回 SDK 或 CLI 完成任务，但页面要诚实地显示为“执行中，完成后展示结果”，不能假装还有正文增量。降级保证任务可用，流式体验则作为独立能力上报。

这个方案还有什么不足？

快照恢复优先保证正确，但会牺牲一点连续感。出现缺口时要重新请求完整状态，长对话的快照也会变大。继续优化的话，我会增加带游标的短期事件重放；只有游标过期才回完整快照。

如果重做一次，你会改什么？

我会更早定义事件契约，并先抓一份真实 trace。一开始就区分生命周期事件、正文 delta 和最终快照，再为重复、乱序、断线写集成测试。这样接 SDK 时就不会因为方法名里有 streamed，默认它等于页面需要的文字流。

面试里不要说：“SDK 无法流式输出。”

准确说法：“在 当时版本 的实测里，SDK 有事件流，但没有拿到满足页面需求的 assistant 正文 delta。”

结果部分不要临时编延迟或性能数字。若有线上记录，再补首字时间、SSE 事件数下降比例和断线恢复成功率。
