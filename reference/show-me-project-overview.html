Local · Spec-driven · Auditable

把一句产品需求，变成一份可运行、可验证、可审查的候选实现。

这个项目是本地规格驱动开发的控制平面。产品经理提供“想要什么”，系统负责收紧边界、组织 Codex 执行、运行真实目标页面，并把每一步变成可核查证据。

核心不是“AI 会写代码”，而是意图、约束、执行、证据与人类责任始终一致。

05 / RECOVERY

可恢复的关键：SSE 是通知，JSON 聚合才是真相

长任务、刷新和断线都不能让浏览器内存成为唯一状态来源。实时性与可恢复性被刻意拆开。

三类状态，各归其位

持久事实

current-requirement.json 与历史快照：阶段、Spec、Tickets、事件、验证、交付。

短期实时

Node 内存中的进程句柄、后台 Promise、SSE 订阅者和 50ms 文本批次。

业务代码

目标仓库中的源码、需求分支和 Git revision；不会复制进 Requirement JSON。

浏览器投影

React Query 按 Requirement 隔离消息；序号缺口触发重新拉取完整快照。

06 / GUARDS

系统真正解决的是“错误怎么被挡住”

每个工程机制都对应一种具体失败模式，而不是为了堆技术名词。

01

产品输入 ≠ Shell

页面只提交标题、站内目标路径和期望结果；命令与仓库地址来自固定配置，缩小命令注入面。

02

幂等键挡住双击

“操作名 + 客户端随机 key”折叠网络重试，不重复建分支、启动进程或创建提交。

03

脏工作区阻断执行

任何已有修改或 merge/rebase 等 Git 操作都会阻断；系统不 stash、不 reset，也不吞掉用户改动。

04

只终止自己拥有的进程

目标服务以独立进程组启动并记录 PID；未知端口占用者不会被扫描或杀死。

05

修改范围二次核验

执行后和验收提交前都重新计算 Git diff；越过 apps/front 的文件会阻断交付。

06

not-run 不能冒充通过

验证矩阵明确区分 verified、failed 和带原因的 not-run；产品语义仍由人类在真实预览上确认。

工作台交付的不是“一段 AI 回答”，而是一条带规格、分支、真实页面、验证证据和稳定 revision 的候选实现链路。

它把 Codex 放进可控工程流程，但把生产合并权和产品语义判断留给人。

它刻意不做什么不自动 push，不创建 PR，不合并主分支，不发布上线，不替产品判断“看起来对不对”，也不替用户处理已有 Git 改动。
