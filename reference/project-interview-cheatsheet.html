Product Agent Workbench

一句主线、四道门、五个难点和事实边界。面试前看这一页，不要临场背整份手册。

一句主线

让产品直接和 Agent 对齐页面需求，但把改代码、判定完成和进入生产的权力拆开。

四道门

意图门

Grilling → 结构化 understanding → 版本化 Spec → Ticket。

执行门

受信配置 → 干净工作区 → 需求分支 → 限定写入 → Turn 后 Git 检查。

验证门

宿主命令 → Runtime → 真实路由 → agent-browser → 产品判断。

交付门

稳定候选 commit + Handoff；前端 Review，不 push、不 merge。

五个难点

  1. 结构化状态机约束自然语言 Agent。
  2. 持久 Requirement 与易失进程跨刷新、重试和重启保持一致。
  3. 用权限加 Git 事实保护真实仓库，而不是只相信 Prompt。
  4. 区分实现失败、环境失败、未验证和产品不接受。
  5. app-server delta 走快路，Requirement 快照走稳路。

流式链路

app-server delta
  → Adapter 累计正文
  → 50ms / 4KB SSE batch
  → React Query 投影

  → 500ms / 32KB 持久化累计全文
  → completed 同 ID 最终校准
  → 断线 / gap / 旧 revision 回到快照

真实结果

真实前端仓库跑通过完整需求：独立需求分支与稳定候选提交；当次 12 项验证为 verified；浏览器证据保存 68 个语义引用，没有新增 console error 或 page error。

不能夸大的地方

  • 当前不自动安装依赖，也不为陌生项目自动猜启动命令和 URL。
  • 真实文字 delta 不等于逐字或逐 token。
  • EventSource 重连不等于补回断线事件。
  • 产品验收不等于生产批准。
  • 没有同口径基线，不报提效百分比。

被追问时的回答公式

“当时出现了什么具体错误 → 哪个事实不能相信 → 我把真值放在哪里 → 用什么门禁或恢复机制处理 → 测试或真实运行怎样证明。”
