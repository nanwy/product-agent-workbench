从进程到消息行

按运行顺序读，不按目录顺序读。每个模块只承担一层协议；箭头跨层时，数据形状会明确变化。

1. codex-app-server.ts

角色：把一个 app-server 子进程包装成一次可等待、可取消的 Turn。

成员含义没有它会怎样
#pendingJSON-RPC request ID → Promise resolve/reject/timer并发请求回来后不知道该唤醒谁
#lineQueue串行消费 stdout JSONLdelta 和终态可能乱序进入业务层
#threadId / #turnId恢复上下文和精确中断当前 Turn只能粗暴杀进程，无法续接 Thread
#turnDone把异步 turn/completed 变成 run() 可 await 的结果启动请求返回后调用方会误以为 Turn 已结束
#settled / #closing防止终态、退出和清理重复结算同一次失败可能 resolve/reject 多次

主函数：run() 做 initialize → thread start/resume → turn start → wait completion → shutdown；#handleLine() 区分 response、server request 和 notification；cancel() 先 interrupt，超时再杀进程组。

2. codex-adapter.ts

角色：隔离 Codex 协议，向业务层只暴露稳定的 Turn 接口。

CodexTurnInput {
  workspaceRoot, prompt, sessionId, signal, sandboxMode,
  onTextDelta(delta),
  onEvent(event)
}
函数输入 → 输出约束
runCodexTurn()统一 Turn 输入 → exitCode + sessionId默认 app-server；SDK 只能显式回退；全局最多一个活动 Turn
appServerTextDelta()原始通知 → delta + 累计 text只接受 agent message delta；item ID 加 Turn scope；进入下游前脱敏
normalizeAppServerNotification()完整 item / turn 通知 → AgentEventdelta 不重复走完整事件路径
normalizeCodexEvent()不同后端事件 → message/tool/file/completed/failed页面和持久层不依赖 app-server 字段名

3. workbench-service.ts

角色：Grilling 和 Spec 的领域编排。它决定回复属于哪条 assistant 消息、什么时候落盘、什么时候允许业务状态前进。

claimGrillingTurn / claimSpecTurn
  → beginAssistantTurn() 创建 streaming 占位消息
  → runCodexTurn()
      onTextDelta: deltaSink.push
      onEvent: flush → applyPlanningEvent → publish invalidate
  → turn 完成后再 flush
  → getWorkbenchSnapshot()

createPlanningDeltaSink() 内有四份局部状态：

  • pending：最后一次收到的累计全文和 item/turn/session 身份。
  • pendingBytes：自上次落盘后新增了多少 UTF-8 字节。
  • timer：500ms 持久化上限。
  • persistence：串行 Promise，防止旧写入晚于最终全文落盘。

push() 做两件并行的事：把原始 delta 交给 SSE 快路；把累计 text 留给持久化稳路。flush() 用累计全文构造 message event，再复用 applyPlanningEvent() 的同 ID 替换规则。

4. workbench-conversation.ts

角色：纯领域状态更新，不关心 SSE 和 React。

函数行为
beginAssistantTurn()追加空 assistant 消息，状态设为 streaming
findStreamingAssistant()从尾部找到当前 Turn 容器，避免改到历史消息
applyPlanningEvent(message)按 item ID 替换或新增 text segment；累计全文不会重复追加
applyPlanningEvent(tool/file)同 ID activity 从 running 替换成 completed/failed
applyPlanningEvent(completed)消息转 completed；根据结构化协议是否完整决定 awaiting-user 或 awaiting-confirmation

5. agent-events.ts

角色：把大量原始 delta 变成浏览器能稳定消费的有序批次。

AgentStreamBatch {
  requirementId, target, targetId,
  turnId, itemId,
  sequenceStart, sequenceEnd,
  revision, delta
}
状态用途
subscribers当前进程内所有 SSE 连接
pending尚未达到 50ms/4KB 的 batch
sequences每个 Requirement + Turn 的下一个连续序号
flushTimer稀疏输出最多等待 50ms

publishAgentTextDelta() 分配序号并合批；item 改变时立即 flush。publishAgentEvent() 先 flush 所有正文，再发布 invalidate，保证终态不会越过正文。

6. api.events.ts

角色：把进程内事件编码成标准 SSE。

: connected

data: {"type":"stream-batch", ...}

: heartbeat

注释行不会触发浏览器 onmessage。15 秒心跳主要防止空闲连接被中间层回收。ReadableStream cancel 时同时清 timer 和 subscriber。

7. workbench-query.ts

角色：唯一的浏览器服务端状态入口。

函数做什么失败策略
applyWorkbenchSnapshot()接收 HTTP/mutation 快照，更新 snapshot 和 conversation queriesRequirement updatedAt 较旧则保留当前值
projectConversation()构造 IDs/byId 读模型，复用未变化对象引用snapshot revision 较旧则不覆盖流式投影
applyAgentStreamBatch()检查序号，不可变追加目标 segment重复忽略；缺口返回 false 让调用方 refetch

8. index.tsx

角色：协调 SSR 首屏、Query、EventSource、轮询和用户 mutation。

loader snapshot → useQuery initialData

EventSource.onopen:
  refetch snapshot → connected=true

EventSource.onmessage:
  stream-batch → applyAgentStreamBatch()
  gap / invalidate → invalidate snapshot

EventSource.onerror:
  connected=false → 3s polling

连接健康时仍有 30 秒校准。它不是实时机制，而是低频保险。

9. workbench-panels.tsx

角色：把 Query Cache 的规范化读模型缩小到组件级订阅。

ConversationTimeline 读取 message IDs；每个 ConversationMessageRow 再用 selector 读取自己的 message。当前 assistant 更新时，历史消息对象引用不变。滚动跟随用 ref 保存，不让每个 delta 触发整棵树的滚动状态更新。
