TaskRun：双 ID 与活动约束

你已经正确写出 requirements。现在只学 TaskRun 表新增的三件事：数据库入队序号、业务 ID、只约束活动状态的唯一索引。

TaskRun 同时有两个身份：enqueue_seq 决定谁先被领取；id 决定业务上这次执行是谁。

先理解 SQLite 的自动整数键

queue_seq INTEGER PRIMARY KEY

这是 SQLite 的特殊规则：声明为恰好 INTEGER PRIMARY KEY 的列会成为内部 rowid 的别名。INSERT 时不提供该字段，SQLite 会自动分配整数，通常是当前最大值加一。

AUTOINCREMENT 不是通用 SQL，也不是“自动生成整数”所必需。它额外保证自动生成的值不会复用这张表历史上用过的旧值，但会维护额外状态并增加开销。

TaskRun enqueue_seq

使用 INTEGER PRIMARY KEY。我们只需要对当前队列稳定排序，TaskRun 也不提供删除用例。

TaskEvent 全局 id

下一课才使用 AUTOINCREMENT。未来即使清理旧事件，也不能复用浏览器见过的 SSE 游标。

先学会逐词读 SQL

如果下面任意关键词陌生，先打开 Migration 零基础语法表。这张表解释本练习会出现的全部语法，不要求你提前学完整 SQL。

id TEXT NOT NULL UNIQUE
id 是字段名；TEXT 是类型；NOT NULL 表示必填；UNIQUE 表示不能重复。
REFERENCES orders(id)
这一列的值必须在父表 orders 的 id 列里存在。
ON DELETE RESTRICT
还有配送任务引用订单时，数据库拒绝删除订单。
CHECK (attempt >= 1)
每次写入时检查 attempt 至少为 1。
status IN (...)
status 只能是括号中列出的字符串；字符串用单引号。
UNIQUE (a, b, c)
a、b、c 三个值组成的组合不能重复，不是三列各自不能重复。
CREATE INDEX
给真实查询建立查找顺序，本身不增加业务字段。
UNIQUE INDEX ... WHERE
只对满足 WHERE 的行检查唯一性，也叫部分唯一索引。

为什么不能有两个 PRIMARY KEY？

enqueue_seq

数据库生成的整数顺序。使用 INTEGER PRIMARY KEY，负责稳定排队。

≠

id

Go 领域生成的字符串身份。使用 TEXT NOT NULL UNIQUE，负责查询和引用。

→

一张表一个主键

主键交给入队序号，业务 ID 用 UNIQUE 获得同样的“不重复”保护。

完整同构示例：配送任务

下面不是项目答案。它和 TaskRun 具有相同结构：一次订单只能有一个活动配送任务，每次重试保留新记录。

CREATE TABLE delivery_runs (
    queue_seq INTEGER PRIMARY KEY,
    id TEXT NOT NULL UNIQUE,
    order_id TEXT NOT NULL
        REFERENCES orders(id) ON DELETE RESTRICT,
    item_id TEXT NOT NULL,
    attempt INTEGER NOT NULL,
    status TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    claimed_at INTEGER,
    started_at INTEGER,
    finished_at INTEGER,
    result_summary TEXT,
    worker_id TEXT,
    delivery_path TEXT,
    failure_reason TEXT,

    CHECK (attempt >= 1),
    CHECK (status IN (
        'waiting', 'claimed', 'running',
        'succeeded', 'failed', 'cancelled'
    )),
    UNIQUE (order_id, item_id, attempt)
);

CREATE INDEX idx_delivery_runs_queue
ON delivery_runs(status, queue_seq);

CREATE UNIQUE INDEX ux_delivery_runs_one_active_order
ON delivery_runs(order_id)
WHERE status IN ('waiting', 'claimed', 'running');

逐块理解

REFERENCES ... RESTRICT
子记录必须指向真实父记录；父记录还有执行历史时禁止删除。
INTEGER / NULL
未发生的 claimed、started、finished 时间保存 NULL；不是用 0 猜状态。
UNIQUE (三列)
同一父对象、同一工作项、同一次 attempt 不能登记两遍。
INDEX(status, queue_seq)
服务“找最早 waiting/queued 记录”这一条真实查询。
UNIQUE ... WHERE
只对活动状态生效；历史上的 succeeded/failed/cancelled 可以存在多条。

先想再核对

问题：为什么部分唯一索引不能把 failed 和 cancelled 也包含进去？

因为失败或取消后必须允许创建 attempt 更大的重试记录。我们只禁止“同时执行两次”，不禁止“保留多次历史尝试”。

问题：为什么 claim 不能只按 created_at 排序？

两个任务可以拥有相同创建时间；数据库生成的 enqueue_seq 才提供无歧义的稳定顺序。

“TaskRun 表没有把业务 ID 和队列顺序混在一起。字符串 ID 用于领域引用，数据库整数序号用于稳定 claim；部分唯一索引只覆盖 queued、claimed、running，并以 Requirement + Ticket 为键，所以无依赖 Ticket 可以并行，同一 Ticket 又不会出现两个活动 attempt。”
