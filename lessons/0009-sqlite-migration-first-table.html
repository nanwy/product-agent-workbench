Lesson 0009 · SQLite Migration

让数据库拒绝错误事实

这节只完成一张表：把 Go 的 Requirement 翻译成 SQLite 的 requirements。完成后，你能亲手写出 migration 练习纸的第一段，并解释每条约束防住什么错误。

Migration 不是“把 struct 搬进数据库”。它是在声明：服务重启以后，哪些事实仍然允许存在。

为什么 id TEXT PRIMARY KEY 还显式写 NOT NULL？SQLite 为兼容旧行为，普通非 INTEGER 主键存在允许 NULL 的历史特例。显式写出约束，意图和行为都更清楚。依据：SQLite PRIMARY KEY。

约束实验：数据库应该接受谁？

依次点击五条输入。不要先背语法，先判断哪条业务规则应该负责拒绝它。

数据库守门员

点击一条输入，查看 PRIMARY KEY、NOT NULL 或 CHECK 如何保护持久化事实。

语法只需要这五块

CREATE TABLE声明一张表，以及列和表级约束。
TEXT / INTEGER本课分别承载文本事实和 revision 整数。
NOT NULL拒绝“这个事实根本没提供”的记录。
PRIMARY KEY给每条记录唯一身份，并建立按 ID 查找的入口。
CHECK (...)每次 INSERT/UPDATE 时检查值是否满足业务边界。

逗号、括号、单引号或关键词仍然陌生时，先看 Migration 零基础语法表，再回来做本页练习。

SQLite 官方说明，CREATE TABLE 可以声明列、类型、主键和 UNIQUE / NOT NULL / CHECK / FOREIGN KEY 等约束；SQLite 使用动态类型系统，所以约束尤其重要。来源：CREATE TABLE、Datatypes In SQLite。

先照着一个完整例子写

下面创建的是文章表，不是本项目的答案，但结构和 requirements 完全同类：

CREATE TABLE articles (
    id TEXT NOT NULL PRIMARY KEY,
    author_id TEXT NOT NULL,
    title TEXT NOT NULL,
    status TEXT NOT NULL,
    version INTEGER NOT NULL,

    CHECK (version >= 1),
    CHECK (status IN ('draft', 'review', 'published'))
);
id TEXT NOT NULL PRIMARY KEY
文本身份；不能为空，也不能和已有文章重复。
author_id / title
普通必填文本：TEXT NOT NULL。
version INTEGER NOT NULL
必填整数；允许范围由后面的 CHECK 负责。
CHECK (version >= 1)
插入或更新时，0 和负数都会被数据库拒绝。
CHECK (status IN (...))
status 只能从括号里的字符串中选择；SQL 字符串使用单引号。

把示例翻译成 Requirement

articles → requirements，author_id → project_id，status → stage，version → revision。然后把三个文章状态换成 domain/requirement.go 中的六个 RequirementStage 字符串。

  2. CHECK 为什么不能只留在 Go 代码里？
  3. PRIMARY KEY 在这个项目里保护了什么身份？

能回答再把 SQL复制到 migration 练习纸 的第 1 步。答不顺就把具体问题带回来问 Agent。

面试时的一句话

“我没有把 Go struct 机械映射成表，而是从 Store 的真实查询和领域不变量反推 migration。第一张 Requirement 表先用主键、非空和 CHECK 约束，保证进程重启后磁盘里也不会出现重复身份、缺失项目、非法阶段或 revision 为零的状态。”
