第二幕：浏览器拿到完整快照后，为什么还要计算 delta？

正确性没问题

每次用最新完整文本替换旧文本，最终内容确实正确。

体验和性能会坏

长回复每来一次更新，都可能提交一次状态并重新解析当前消息的 Markdown。如果 Store 用一个大数组、时间线又订阅整个数组，100 条历史消息还可能一起收到更新；滚动位置也可能持续跳动。

所以浏览器做两个彼此独立的性能优化。第一，已显示 我建议，新快照是 我建议先确认，确认前缀关系后只把尾部 先确认 放进缓冲区，并在下一动画帧统一提交。第二，消息保存为 messageIds + messagesById，每一行只订阅自己的 ID；没有变化的历史消息复用原对象引用。

注意：这不等于 DOM 只渲染“先确认”三个字。刷新时，当前消息组件仍然拿到累积后的完整正文并重新渲染；真正减少的是状态提交次数，以及被波及的消息行数量。

effective = 已显示正文 + 尚未刷新的 pending delta

if incoming.startsWith(effective):
    delta = incoming.slice(effective.length)
else:
    直接采用 incoming 完整快照

第三幕：为什么一定要做前缀校验？

模型或上游协议不一定永远只在末尾加字。假设浏览器已有：

current  = "请修改登录页"
incoming = "请只修改登录页"

新文本在中间插入了“只”。如果仍按旧长度硬切尾巴，会算出一段毫无意义的字符，再追加到旧句子上。项目因此只在 incoming.startsWith(effective) 成立时计算 delta；不成立说明历史被修订，立即丢弃动画投影，采用服务端完整快照。

delta 是可丢弃的加速缓存，不是事实来源。任何拿不准的情况都回到完整快照。

第四幕：网络在中间断了，会发生什么？

如果 SSE 直接承载 delta

收到："我建议"
断线，漏掉："先确认"
重连后收到："目标页面"
页面："我建议目标页面" ❌

除非额外实现事件序号、持久事件日志和补放协议，否则漏掉的 delta 没办法凭空恢复。

本项目：SSE 只发“有变化”

收到通知 → GET Requirement 完整快照
断线漏通知 → 3 秒轮询触发 GET
拿到："我建议先确认目标页面" ✅

通知可以丢，因为通知里没有唯一真值。页面只要再次读取 Requirement，就会收敛到正确状态。

这也是为什么断线重连不会重放“创建分支、执行 Ticket”之类的副作用：SSE 不是命令通道，只是失效通知。浏览器原生 EventSource 会尝试重新建立连接，但“重新连上”不等于“自动补回断线期间的事件”。本项目没有维护可重放的 SSE 事件日志，因此完整 Requirement 快照负责补状态，轮询负责在没有下一次通知时也能触发读取。

检索练习 3：断线恢复时，哪一个能作为可靠真值？

第五幕：五段链路各自只解决一个问题

1Codex SDK产出结构化事件；正文当前通常完成后一次到达
2Adapter统一类型；用 turn + item 组成稳定 ID
3Requirement同 ID 替换；持久化完整消息和状态
4SSE + 轮询通知页面重新读取权威快照
5Zustand安全切 delta；按帧合并；按 ID 重绘

没有稳定 ID

工具会出现“读取中”“读取完成”两行，甚至不同 Turn 的同名 item 相互覆盖。

没有持久快照

刷新页面或服务重启后，只剩零散事件，无法知道当前完整对话和门禁状态。

没有按帧合并

假设 16ms 内到达 20 次更新，React 可能收到 20 次状态提交；合帧后这一帧只提交 1 次。

还有三个容易被忽略的坑

未闭合 Markdown

```ts 已到达但结尾围栏没到时，解析器可能不断重排。项目先把未闭合部分当纯文本 <pre>，闭合后再交给 Markdown。

业务门禁提前打开

文本里刚出现 READY，不代表结构化理解完整，也不代表 Turn 已结束。项目要求“完整 JSON + READY + turn.completed”后才允许产品确认。

自动滚动抢阅读

用户在底部才自动跟随；用户上滚后停止抢位置，只显示“回到底部”。否则长回复会把正在阅读历史的用户拖走。

把技术选择还原成一句因果链

“我先区分事件流和文字流。当前 TypeScript SDK 包装的是 codex exec --experimental-json，会持续给出工具、文件、todo 和生命周期事件，但 assistant 正文通常在 item.completed 一次返回，并不是真正的逐字流。工作台把服务端 Requirement 作为唯一真值，SSE 只通知浏览器重取快照，三秒轮询负责漏通知后的最终收敛。前端还保留了增长快照转 delta、前缀失败回退和 rAF 合帧能力，这是防御性和前向兼容设计；要实现真正 token 级文字流，需要改接 app-server 的 item/agentMessage/delta。”
