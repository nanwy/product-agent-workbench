Lesson 0002 · 完整链路

只追踪一条回复

先不背五层架构，也不做下一道题。我们只看一句“建议只修改登录页”从 Codex 产生，到服务端保存，再到浏览器显示的全过程。

一、先分清三个东西

服务端真值

Requirement JSON 中的完整对话。刷新、断线和恢复都以它为准。

→

变化通知

SSE 只表达“真值变了，请重新读取”，自身不承担恢复。

→

浏览器投影

Zustand 中为流畅显示维护的副本。必要时可以整个丢掉并从真值重建。

整套设计只有一个总原则：服务端负责“内容绝不能错”，浏览器负责“显示尽量顺”。优化失败时牺牲动画，不能牺牲正确性。

二、为什么不能只有一个状态？

只把状态放浏览器

页面一刷新，内存里的回复、工具状态和确认门禁全部消失。断线时也不知道缺了哪些内容。

每次直接重画服务端全量状态

正确性成立，但高频快照会反复提交状态、解析当前 Markdown；如果数据结构和订阅边界也很粗，历史消息还会被一起波及。

因此项目保存一份可靠的服务端快照，同时允许浏览器维护一份可随时重建的流畅投影。这不是重复造状态，而是把正确性职责和显示职责拆开。

三、一次回复的真实运行顺序

  1. 先在服务端创建一条 streaming 占位消息

    workbench-service.ts → claimGrillingTurn() → beginAssistantTurn()

    用户提交需求或回答问题后，服务端先把 Conversation 改成 running，追加一条空的 assistant 消息，状态为 streaming，然后原子写入 Requirement。

    原因：后续所有 SDK item 都有一个确定的回合容器；双击或两个页面同时触发时，只有第一个请求能认领这个回合。

  2. Codex SDK 开始产生结构化事件

    codex-adapter.ts → runCodexTurn() → thread.runStreamed()

    SDK 会依次产生 thread、tool、file、todo、completed、failed 等结构化事件，但这不等于正文逐字输出。项目实测中，一份数千字 Spec 直接出现在单个事件里：

    item.completed  id=msg-7  text="建议只修改登录页"

    底层 app-server 才有 item/agentMessage/delta。项目测试夹具里的 item.updated → item.completed 增长正文，是为了验证兼容性，不是当前 exec 的实测事件序列。

  3. Adapter 把 SDK 方言变成工作台稳定事件

    codex-adapter.ts → normalizeCodexEvent()

    原始事件被统一成 message / tool / file / completed / failed。ID 由 turnEventScope + SDK item ID 组成。

    为什么要稳定 ID：同一个工具从 running 到 completed 应更新原卡片；如果未来同一消息出现多次快照，也应更新同一段文字。再加 Turn 作用域，是为了避免下一回合碰巧复用相同 item ID 时覆盖上一回合。

  4. 先更新并持久化 Requirement

    workbench-service.ts → onEvent() → requirementStore.update() → applyPlanningEvent()

    applyPlanningEvent() 找到当前 streaming assistant 消息。当前真实路径通常是在 item.completed 到达时一次写入 msg-7 = "建议只修改登录页"。若收到同 ID 的后续消息快照，则替换原 segment；工具活动也按 ID 从 running 替换成 completed。更新操作进入串行队列，写临时 JSON 后原子 rename，因此读取方只会看到旧完整文件或新完整文件。

  5. 持久化成功后，SSE 才按门铃

    workbench-service.ts → publishAgentEvent() → api.events.ts

    顺序是 await store.update()，然后才 publishAgentEvent()。浏览器虽然能收到事件 JSON，但当前页面并不拿它直接修改对话，只把 onmessage 当作刷新信号。

    如果先通知再保存：浏览器可能立即读取到旧快照；若之后没有新通知，页面会暂时停在旧状态。

  6. 浏览器重新 GET 完整 WorkbenchSnapshot

    index.tsx → EventSource.onmessage → getWorkbench() → setSnapshot()

    SSE 到达后，页面调用服务端函数重新读取 Requirement。与此同时还有三秒轮询走同一条读取路径。

    SSE 的价值：快。轮询的价值：漏掉通知后仍会再读。完整快照的价值：告诉浏览器缺失期间最终变成了什么。

  7. hydrate 把服务端快照投影到 Zustand

    index.tsx → conversationStore.hydrate()

    对于已完成的历史消息，内容相同就复用旧对象引用。只有当数据源真的产生“正在增长的完整消息快照”时，才比较：

    effectiveContent = 页面已经提交的正文 + pending delta

如果 incoming 以 effectiveContent 开头：
  只把尾部差异放入 pending
否则：
  清掉 pending，直接采用 incoming 完整快照

    这里的 delta 只是浏览器内部优化。服务端并没有丢掉完整正文，SSE 也不是唯一数据来源。

  8. requestAnimationFrame 把多次 delta 合成一次状态提交

    conversation-store.ts → appendDelta() → schedule(flush)

    同一帧内若有多次增长快照，尾部差异先积累在闭包 Map 里。下一次绘制前，flush() 一次性把它们追加进当前消息。当前 exec 一次给全文时，这段逻辑不会制造逐字动画。

    屏幕已有：建议
pending 1：只修改
pending 2：登录页

一帧只提交一次：建议只修改登录页

    这减少的是当前消息的状态提交次数，不是只创建“登录页”三个字的 DOM。

  9. 只有变化的消息行响应 Store 更新

    workbench-panels.tsx → ConversationMessageRow

    时间线订阅 messageIds，每行再按自己的 ID 订阅 messagesById[id]。第100条消息增长时，前99条保持相同引用，因此不会跟着重新渲染。

    当前行仍用完整正文渲染。只有接入真正的增长快照或文字 delta 后，未闭合代码围栏处理才会成为实时渲染中的必要优化。

  10. Turn 完成时，用服务端最终快照收口

    applyPlanningEvent() → event.type === "completed"

    服务端把消息从 streaming 改成 completed，并决定 Conversation 是等待用户回答，还是开放确认。浏览器下一次 hydrate 看到终态后，不再计算流式 delta，而是直接采用完整最终消息。

    Grilling 中即使文字已经出现 READY，也必须同时拿到完整 understanding，随后收到 turn.completed，才进入 awaiting-confirmation。这样半截控制协议不会误开门禁。

五、每个设计到底保住了什么

设计不这样做性质
同 ID 更新同一 item工具的 running/completed 变成重复卡片；未来增长快照也可能重复正确性
Requirement 保存完整快照刷新、断线或重启后无法重建当前对话正确性
先持久化再发 SSE收到通知却读到旧值，形成通知与数据竞态正确性
SSE 只通知，轮询兜底漏一次事件可能永久停留在旧状态可恢复性
前缀校验后计算 delta上游修订历史文字时，客户端拼出错误文本正确性
rAF 合并 pending当前消息在一帧内重复提交和渲染性能体验
按 ID 订阅消息行当前消息增长可能波及整段历史性能体验
隔离未闭合 Markdown代码围栏未闭合时反复重排和高亮性能体验
完整协议 + completed 门禁半截 Agent 输出可能提前开放产品确认业务正确性

六、三个看起来更简单的方案，为什么没用

SSE 直接承载所有业务状态

断线时会漏掉状态；工具 running/completed 若不按 ID 归并，还会出现多张重复卡片。

SSE 只发送字符 delta

正常时简单，但断线后必须另外建设事件序号、持久日志和补放协议。当前单机工作台用“通知 + 完整快照”更容易证明正确。

浏览器永远全量替换

这个方案不会导致内容错误，也适合作为最小版本；项目增加 delta、rAF 和按 ID 订阅，是为了长对话与 Markdown 流式更新时仍然顺滑。

七、面试时应该怎么讲

“我先区分了事件流和文字流。当前项目通过 Codex SDK 包装的 codex exec --experimental-json 接收结构化事件：工具、文件和 todo 会在执行中更新，但 assistant 正文通常在 item.completed 一次返回，所以现阶段不能宣称实现了 token 级文字流。我的核心设计是把事件按 Turn 作用域和 item ID 归一化，先原子持久化 Requirement，再由 SSE 通知浏览器重取完整快照，并用三秒轮询兜底。这样断线或漏通知后仍会收敛到服务端真值。前端的安全 delta、pending 和 rAF 是对增长快照的兼容与性能准备；如果产品确实需要逐字效果，下一步应接 app-server 的 item/agentMessage/delta，而不是误解现有 SDK 事件。”

首选资料：OpenAI Codex exec JSONL 事件处理器。真实实现入口见 workbench-service.ts、codex-adapter.ts、conversation-store.ts和workbench-panels.tsx。有任何一步不清楚，可以直接把那一步的编号发给 Agent。
