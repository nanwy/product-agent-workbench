先用前端语言翻译整个后端

你不是在学习一套完全陌生的东西。很多后端结构，在前端已经以组件、状态管理、请求封装和异步任务的形式见过；区别是后端必须对并发、进程崩溃和持久化结果负责。

React reducer / 状态机→ Domain

根据当前状态和动作计算下一个合法状态。例如 TaskRun 只有 running 才能 complete。

事件处理函数 / mutation→ Application

编排一次用户动作：读取数据、调用领域规则、保存结果，但不关心 HTTP 细节。

API client / 数据访问层→ Store

隐藏 SQLite 查询细节。它比 Zustand Store 更接近前端项目里的 repository 或持久化 adapter。

derived selector→ Scheduler

根据 Ticket DAG 和执行历史算出 ready Ticket；不同点是它还会把结果可靠写成 queued TaskRun。

受限并发 Promise 队列→ Supervisor

类似 p-limit：只允许固定数量异步任务同时运行，并等待这一批全部结束。

一次 mutation 流程→ Worker

类似 mutationFn：领取任务、改成 running、调用执行器，再保存 success/error；但状态在数据库，不在浏览器内存。

AbortSignal→ context.Context

沿调用链传递取消和截止时间。它不保存业务状态，也不应该塞成全局数据容器。

WebSocket RPC Client→ JSONRPCConnection

给请求编号，用 Map 保存 Promise resolver；收到响应后按 ID 找回对应等待者。

App 根组件 / Provider 组合→ main 依赖装配

在唯一入口创建真实实现，再注入下层。类似在 App 根部组装 QueryClient、Router 和各种 Provider。

前端转全栈最重要的变化： 前端通常假设刷新页面后可以重新请求；后端不能假设进程永远活着。因此 queued、running、事件序号、ownership 和 Git revision 都必须成为可恢复的持久事实。

练习 15：并发执行与代码隔离

15A · 编排层

Supervisor + ManagedRunner

Supervisor 控制“同时最多跑几张票”；ManagedRunner 控制“每张票必须在自己的 Worktree 里跑”。

15B · Git Adapter

真实 Git Worktree

用参数数组调用 Git，记录 ownership，检查修改范围，并把 Ticket 分支安全整合回 Requirement 分支。

前端类比： 把 Supervisor 想成带并发上限的请求池，把 Worker 想成一次 mutation，把 ManagedRunner 想成 mutation 外面包的一层安全事务。区别是这里操作的不是 UI 状态，而是真实数据库、进程和 Git 仓库。

15A：谁负责并发，谁负责一次任务？

Supervisor 创建固定数量的 Workerinternal/runner/supervisor.go · NewSupervisor

例如并发数为 2，就只有两个槽位；不会每来一张票就无限创建 goroutine。

每个槽位循环调用 Worker.RunNextinternal/runner/supervisor.go · drainWorker

多个 Worker 会竞争 SQLite 的原子 claim，因此同一条 TaskRun 只会被一个 Worker 领到。

Worker 推进 TaskRun 状态internal/runner/worker.go · RunNext

queued → claimed → running，然后才调用 Executor；成功后 completed，失败后 failed。

ManagedRunner 包住真正 Executorinternal/runner/managed_runner.go · Run

Worker 不需要知道 Git；它只看到一个仍然满足 runner.Runner 接口的对象。

15B：一张 Ticket 的 Git 生命周期

Prepare从 BaseRevision 建 Ticket 分支
ExecuteCodex 只修改独立 Worktree
ChangedFiles拒绝空修改
Scope Check拒绝允许范围外文件
Commit保存 Ticket 修改
Integrate非快进合并到 Requirement 分支

为什么每票一个 Worktree？

A、B 没有业务依赖，可以并行；如果共用一个目录，它们仍会争抢文件、分支和 index。Worktree 把“业务并行”变成“代码目录也隔离”。

为什么整合仍要串行？

两个 Ticket 可以同时开发，但 Requirement 分支是共享写入点。integrationMu 让 merge 一个一个发生，冲突时保持目标分支不被半写入。

ownership 有什么用？

证明某个目录确实由本程序创建。重启后只有记录与 Git 事实都一致才恢复；陌生目录不接管、不删除。

15 和 16 的接口在哪？

ManagedRunner 内部持有另一个 Runner。15 先准备 Worktree，再把路径写入请求，随后调用 16 的 Executor.Run。

练习 16：真实 Codex Adapter

16 被拆成四层。点击标签只看一层，先建立职责边界，再读实现。

前端类比： 如果你写过 WebSocket client，16 就很好理解：16A 是底层 socket 消息分发，16B 是连接资源的创建与销毁，16C 是业务 API client，16D 是把它包装成 React Query 的 mutationFn 所期待的“输入请求、返回结果”。
16A · 传输层

把并发 Go 调用变成不会串行错乱的 JSONL

发请求

  1. Request 分配递增 ID
  2. 把等待者放入 pending[id]
  3. 消息交给唯一 writeLoop
  4. 响应回来后按 ID 唤醒正确请求

收消息

  1. 唯一 readLoop 按行读取 stdout
  2. 有 ID 的响应 → pending 请求
  3. 无 ID 的通知 → NotificationSink
  4. 服务端反向请求 → RequestHandler

核心不变量：只有一个 goroutine 写 stdin，避免两段 JSON 字节互相穿插；只有一个 goroutine 读 stdout，保留通知到达顺序。

用前端写法理解 pending map 
const pending = new Map<number, {
  resolve(value: unknown): void
  reject(error: Error): void
}>()

function request(method, params) {
  const id = nextId++
  send({ id, method, params })
  return new Promise((resolve, reject) => {
    pending.set(id, { resolve, reject })
  })
}

function onMessage(response) {
  pending.get(response.id)?.resolve(response.result)
  pending.delete(response.id)
}

Go 没有直接使用 Promise，而是用 pending map + channel 表达“请求先等待，响应到达后唤醒”。

16B · 进程层

启动并可靠回收 app-server

exec.Command(codex, "app-server", "--listen", "stdio://")
  stdout ──→ JSONRPCConnection.Input
  stdin  ←── JSONRPCConnection.Output
  stderr ──→ 有上限的 tailBuffer
  • 不经过 Shell：产品文字不能变成命令参数注入。
  • stdout 只放协议消息；stderr 只保留有限诊断尾部。
  • 只有内部一个 goroutine 调用 cmd.Wait()，避免重复回收。
  • 正常关闭先关 stdin；超时后 Unix 上终止整个进程组。

前端对应：像在组件挂载时创建 WebSocket、卸载时 close；但子进程比 WebSocket 更重，还必须调用 Wait 回收，否则可能留下僵尸进程。

16C · 协议层

按 app-server 规定的顺序说话

initialize请求并等待响应
initialized单向通知
thread/start或 thread/resume
turn/start发送 Prompt
turn/interrupt取消时使用

AppServerClient 不启动进程，也不保存 TaskRun；它只把“协议顺序和参数形状”封装起来。

前端对应：类似 api.login()、api.createSession() 这样的 typed client。页面不应该到处手写 fetch method、URL 和 body；Executor 也不应该到处手写 JSON-RPC method。

16D · 业务适配层

把进程、Client、通知和 Runner 结果串成一次 Turn

  1. 创建 eventEmitter，它立即启动后台 loop()。
  2. 启动 app-server，并把 observer.Handle 注册为通知接收器。
  3. initialize，创建或恢复 Thread，持久化 session 事件。
  4. 启动 Turn；observer 解析文本增量、item 和完成通知。
  5. 只有收到 turn/completed 且状态为 completed，才返回成功结果。
  6. 业务 context 取消时发送 turn/interrupt，最后再关闭进程。

前端对应：它很像一个复杂 mutationFn：收到输入后创建资源、订阅增量、等待终态、处理 abort，最后返回统一结果。不同点是它不负责页面缓存，而是把事件交给 EventSink。

Handle(notification)
  emitJSON(ctx, "codex.text.delta", value)  // 这里给出字符串
    o.emit(ctx, eventType, payload)          // 作为实参传给回调

        requests <- eventRequest{eventType: eventType}

它不是全局变量，也不是之后自动生成的字段。每种通知分支在调用 emitJSON 时明确给出事件类型。

为什么 Emit 要等 ack，而不是扔进 channel 就返回？

因为事件持久化失败后，Runner 必须停止产生“已经执行但无法审计”的后续工作。Emit 等待 loop 调用 EventSink 的结果；失败会原样返回给 observer 和 Executor。

前端类比： EventSink 很像一个 callback prop：组件只负责调用 onChange(value)，至于父组件把值写进 Zustand、发到接口还是忽略，由装配者决定。同理，eventEmitter 只调用 sink(ctx, event)，它不知道 sink 最终是不是 SQLite。

这些类比有边界，不要完全画等号

Store ≠ Zustand Store

这里的 Store 是持久化接口，背后是 SQLite；进程退出后数据仍在。

goroutine ≠ Web Worker

goroutine 是 Go 运行时调度的轻量并发任务，共享同一进程内存，不是浏览器隔离线程。

channel ≠ EventEmitter

channel 有阻塞、关闭和背压语义；不仅是发布订阅回调列表。

context ≠ React Context

context.Context 主要传取消、超时和请求级元数据，不用于保存业务对象。

Worker ≠ 浏览器 Web Worker

本项目的 Worker 是业务对象名称：消费一条 TaskRun；它不对应某一种操作系统线程。

TaskEvent ≠ UI 唯一真值

事件用于审计和增量展示；刷新恢复时仍要查询 TaskRun/Requirement 的持久化快照。
