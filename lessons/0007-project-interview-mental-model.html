Lesson 0007 · 项目总览

不要背功能，记住四道门

这节课只建立项目骨架。学完后，你应该能拿一条页面文案需求，从产品输入一路推演到候选提交，并说出每一步在防什么错误。

Agent 负责生成候选结果；工作台负责授权、约束、验证和留证。这个分工就是整个项目。

一条需求怎样走完

产品输入页面 + 结果
意图门Grilling / Spec
执行门Git / Codex
验证门命令 / 页面
交付门Commit / Handoff

例子是：“修改 /competition 的空状态文案，但不能影响后台和其他列表页。”不要先想组件。先问：什么结果算对，哪里不能动，用什么证据判断。

四道门分别拦什么

1意图门

Agent 先查事实、再问业务决策。合法 understanding、当前 Spec 版本和产品确认同时满足，才允许继续。

没有它：Agent 带着错误假设开工，或者拿旧 Spec 实现。

2执行门

固定配置、干净 working tree、需求分支、限定可写根，以及 Turn 后 Git 检查共同约束执行。

没有它：用户改动被混入，未跟踪文件或范围外文件进入候选提交。

3验证门

Agent 退出不等于需求完成。宿主命令、运行时、真实路由、浏览器证据和产品判断分别留证。

没有它：环境失败被当成代码失败，没运行的检查被写成通过。

4交付门

产品验收后冻结候选 revision，把 Spec、Tickets、验证和风险一起交给前端；不自动 push 或 merge。

没有它：产品“看起来可以”被误解成代码可以上线。

三份真值不要混

对象保存什么坏了怎样恢复
Requirement需求、Spec、Ticket、执行、验证与交付事实从 JSON 权威快照恢复
目标 Git代码、base revision、需求分支和 diff重新检查分支、HEAD、tracked 与 untracked
活运行态Codex Turn、SSE 订阅、后台 Promise、开发进程心跳判断旧进程是否消失，重新启动或标记可重试

浏览器不是第四份真值。React Query 只是 Requirement 的投影。SSE 用来快速通知和追加文字，断线或序号缺口后仍回到服务端快照。

现在闭卷回答

问题一：为什么 Spec 不能只放在聊天记录里？先用自己的话回答，再核对。

聊天记录包含已经失效的讨论，不能表达“当前哪一版获得授权”。版本化 Spec 把有效意图冻结下来，Ticket 和验收条件都基于同一版本。

问题二：已经创建需求分支，为什么还要检查 working tree 和修改范围？

分支不保护未提交改动，也不阻止 Agent 写到其他目录。干净工作区保护用户现场，可写根与 Git diff 保护确认范围。

问题三：Agent 返回 0，为什么还不能开放产品验收？

返回 0 只证明 Turn 正常结束。代码是否通过检查、服务是否可运行、页面是否可访问、业务结果是否正确，都需要独立证据。

问题四：SSE 已经实时推送，为什么还需要 Requirement 快照？

SSE batch 是瞬时快路，刷新和断线会漏。Requirement 保存累计全文和最终状态，是客户端发现缺口后重新收敛的依据。

面试开场只说这一段

“我做了一个本地 AI 研发工作台，解决产品需求要先解释给前端、再由前端转述给 Agent 的重复沟通。产品先和 Agent 对齐目标、边界和验收信号，确认版本化 Spec 和 Ticket 后，Codex 才能在真实仓库的独立分支和限定目录里工作。工作台负责项目运行、Git 越界检查、构建和真实页面证据，产品负责页面验收，前端决定是否合并。它的核心不是让 Agent 多写代码，而是用四道门把不确定的生成过程变成可以审查的候选交付。”
