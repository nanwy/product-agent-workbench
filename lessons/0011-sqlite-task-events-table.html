TaskEvent：全局 ID 与局部 Sequence

事件表只学一个核心区别：全局 ID 回答“整个系统漏了哪些事件”，Sequence 回答“某个 TaskRun 内下一条应该是多少”。

id 是跨任务的 SSE 游标；sequence 是单个 TaskRun 内的连续顺序。它们不能互相替代。

这里为什么才使用 AUTOINCREMENT？

AUTOINCREMENT 是 SQLite 特有语法，只能跟在 INTEGER PRIMARY KEY 后面。它不是为了让数字连续——事务失败等情况仍可能留下空洞。

它保证自动生成的新值大于这张表历史上出现过的值，不复用删除行的旧 ID。事件 id 会成为浏览器保存的 Last-Event-ID；未来即使清理旧事件，也不能让新事件重新拿到浏览器见过的 id，所以这里才值得使用。

这张表只新增一个类型：BLOB

payload BLOB NOT NULL
payload 是字段名；BLOB 表示原始字节；NOT NULL 表示每个事件必须有 payload。
Go []byte → SQLite BLOB
数据库原样保存字节，不把它自动解释成 JSON 或文本。
UNIQUE (run_id, sequence)
同一次 run 内不能重复 sequence；不同 run 都可以从 sequence=1 开始。

其他关键词都在 Migration 零基础语法表 中逐词解释。

完整同构示例：配送事件

CREATE TABLE delivery_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    delivery_run_id TEXT NOT NULL
        REFERENCES delivery_runs(id) ON DELETE RESTRICT,
    sequence INTEGER NOT NULL,
    type TEXT NOT NULL,
    payload BLOB NOT NULL,
    created_at INTEGER NOT NULL,

    CHECK (sequence >= 1),
    UNIQUE (delivery_run_id, sequence)
);

为什么每一项都存在

id

数据库生成且不复用的全局整数。未来 SSE replay 使用它作为跨 TaskRun 游标；允许有空洞。

sequence

调用方提供的局部顺序。UNIQUE 防止同一 TaskRun 重复写入相同序号。

payload BLOB

Go 的 []byte 原样保存，不依赖数据库重新编码 JSON 文本。

外键 RESTRICT

事件必须属于真实执行；有审计事件的执行不能被静默删除。

问题：批次是 sequence 3、5，为什么不能先写 3，再因为 5 错误而返回？

因为调用方收到失败后会认为整批没有发生；如果 3 已落盘，重试又会遇到重复序号，数据库事实和调用方认知分裂。必须整批提交或整批回滚。

问题：为什么不只保留全局 id？

全局 id 中会穿插其他 TaskRun 的事件，不能证明 run-A 自己是否漏掉 sequence 2。局部 sequence 才表达单次执行内部的连续性。

“事件表同时保存全局 ID 和 TaskRun 局部 sequence：前者给 SSE 断线 replay 使用，后者保证单次执行内部不重不漏。批量追加放在一个事务里，先验证完整批次，失败时不部分写入，也不消耗对调用方可见的事件进度。”

主参考：SQLite CREATE TABLE、SQLite AUTOINCREMENT、SQLite Foreign Keys。写不下去时，把具体字段或约束带回来问 Agent。
