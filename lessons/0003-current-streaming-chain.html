Lesson 0003 · 当前实现总览

一条回复有三种形态

这次先不看函数名。只追踪“建议只修改登录页”怎么从 app-server 到达页面，再怎么变成刷新后仍然存在的服务端真值。

页面追求快，服务端负责不丢，完成全文负责纠错。三个职责由三种数据承担，不能混成一个状态。

先认清三种数据

原始 delta

"建" → "议" → "只修改" → "登录页"

app-server 的 item/agentMessage/delta 是可以直接按顺序追加的片段。它不是累计全文。

SSE 批次

batch[1..2] = "建议"
batch[3..4] = "只修改登录页"

后端把短时间内同一个 item 的多个 delta 合起来，减少浏览器更新次数。

权威全文

item.completed.text =
"建议只修改登录页"

完成事件里的全文用于持久化和校准。页面临时拼错、漏包或刷新，都回到它。

和旧实现的区别：以前的 codex exec 通常只在 item.completed 给完整正文。现在默认走 app-server，能接到真正的 item/agentMessage/delta。真实上游不保证逐字；本项目冒烟中，“通过”两个字就是一个 delta。

为什么有 50ms、500ms 和 completed 三个时钟

立即：接收

每个原始 delta 一到，就分配连续序号，并累计当前 item 的全文。

目标是先把数据接住。

50ms / 4KB：显示

同 item 的碎片合成一个 SSE 批次。文字少时最多等 50ms，文字多时达到 4KB 立即发。

目标是页面顺滑。

500ms / 32KB：保存

累计全文定期写进 Requirement。就算进程中断或用户刷新，最多损失很短的一段临时显示。

目标是可恢复。

item.completed：校准

先处理完所有 pending delta，再用同 item ID 的完整正文替换临时内容。

目标是最终正确。

逐步推演：每按一次，系统往前走一步

同一份数据为什么要走两条路

快路：delta → SSE → Query Cache

不等待磁盘，不重新 GET 全量快照。页面很快看到增长中的正文。

这条路允许失败。重复批次可以忽略，缺批次就放弃本地拼接。

稳路：累计全文 → Requirement → HTTP 快照

写入慢一点，但内容完整。断线、刷新、漏事件、最终完成都从这里恢复。

这条路决定事实。

如果只走快路，断线漏掉“只修改”，页面可能变成“建议登录页”。如果只走稳路，每个碎片都落盘并重新拉快照，能做对，但会频繁写文件和刷新大对象。现在的设计把两件事分开。

你应该能自己说出的因果链

  1. app-server 给的是可追加 delta，item.completed 给的是权威全文。
  2. 后端先接住每个 delta，再按 50ms 或 4KB 合批给页面。
  3. 同一份累计正文按 500ms 或 32KB 写入 Requirement。
  4. 终态前先 flush，保证 delta、工具事件、完整正文的顺序不乱。
  5. 浏览器发现重复序号就忽略，发现缺口就重取快照。
离开页面回答：

为什么已经有 SSE delta，还要保存累计全文？为什么已经保存累计全文，还要再处理 item.completed？不要用“更稳定”这种空话，分别说出断线和上游修订时会发生什么。

首选资料：OpenAI Codex app-server 协议。官方定义同一 item 的 delta 应按顺序拼接，并把 item/completed 当作最终 item 状态。项目入口见 codex-app-server.ts 和 codex-adapter.ts。卡住时直接把推演时刻 T0–T8 发给 Agent。
