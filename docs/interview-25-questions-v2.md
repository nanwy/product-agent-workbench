# 智能产品研发工作台：25 道深挖面试问答

这份材料基于 `docs/interview-retrospective.md` 整理。它不是功能清单，而是一套可以连续讲下去的答题口径：先说明项目为什么存在，再讲设计选择，最后落到代码、验证和团队试点结果。

## 如何用 90 秒介绍智能产品研发工作台？

别名：90 秒介绍工作台、用一分钟半讲清研发工作台、智能产品研发工作台开场介绍

我做的是一个本地 AI 研发工作台，主要解决页面需求在“产品、前端、Agent”之间重复转述的问题。

以前产品先写文档或原型，再向前端解释一遍。前端补齐文案、状态和修改边界后，往往还要把同一件事重新组织成 Prompt 交给 Agent。代码生成确实变快了，但需求对齐、项目上下文和验收并没有消失。

所以我没有把它做成一句话生成代码的工具，而是保留正常研发流程。产品先和 Agent 对齐目标结果、修改边界和验收信号，确认后生成有版本的 Spec，再拆成能独立交付的 Ticket。实现前，系统检查真实仓库的 Git 状态，并从固定 revision 创建独立需求分支。Agent 只能读取项目自己的 `AGENTS.md`、README 和 Skill，并在确认范围内修改代码。

代码完成后，也不是由 Agent 自己宣布成功。工作台在宿主环境运行 typecheck、测试和 build，再启动真实项目，通过目标路由检查页面、可访问性树和控制台错误。产品负责页面结果是否符合需求，前端保留代码审查和生产合并权。最终交付的是候选提交、Spec、Tickets、验证矩阵和 Handoff，而不是一段聊天记录。

这个项目已经在一个前端、一个后端和一个产品组成的小组里试点。真实前端仓库的一次完整需求留下了 12 项通过记录、68 个页面语义引用，并且没有新增 console error 或 page error。

## 智能产品研发工作台解决的是前端效率问题，还是通用研发问题？

别名：工作台只解决前端问题吗、研发工作台是通用平台吗、这个项目的适用范围是什么、工作台能否支持后端

我会先把边界说清楚：当前落地场景是前端页面需求，不会把它包装成已经支持所有技术栈的通用研发平台。

但我抽象的不是某个 React 页面生成器，而是一条研发控制链：需求对齐、版本化 Spec、任务拆分、受控执行、真实验证和候选交付。React、Vite、Next.js 属于当前接入层；状态门禁、Git 隔离、执行恢复和验证证据是可以复用的。

比如现在验证页面会启动前端服务并访问真实路由。如果将来接后端需求，这一层可以换成启动 API 服务、执行迁移和接口测试，但“先确认范围、再执行、最后用外部证据验收”这条主线不需要重写。

## 智能产品研发工作台的整体技术架构是什么？

别名：工作台整体架构、研发工作台五层架构、工作台各模块怎么协作、介绍一下工作台的技术架构

我把系统分成五层。

第一层是需求域。Requirement 是聚合根，里面保存共同理解、Spec 版本、Ticket 状态、验证结果、Thread ID、Git 分支和交付信息。

第二层是 Agent 编排。默认接 Codex app-server，负责创建或恢复会话、发送 turn，并把文字、工具、文件、完成和失败事件归一化。旧 SDK 只保留显式回退。

第三层是执行边界。它检查 Git 状态、创建需求分支、限制可写目录，并在每个 turn 前后比较 tracked 和 untracked 文件，避免 Agent 越界。

第四层是运行和验证。Target Runtime 管理开发服务和健康检查，预览网关代理 HTTP 与 WebSocket，宿主执行 typecheck、测试和 build，浏览器检查真实路由和控制台。

第五层是前端状态。服务端快照是权威数据，SSE 只传实时增量，React Query 负责缓存、投影和断线后的重新获取。

举个完整例子：产品要求修改 `/competition` 的空状态文案。需求域先生成 Spec 和 Ticket；执行层创建独立分支；Codex 修改候选文件；Runtime 启动前台应用；验证层检查目标路由和 console；最后 Requirement 里保存这次需求的代码、证据和验收结论。

## 智能产品研发工作台为什么要拆多个阶段？

别名：为什么不用一个大 Agent 从头做到底、工作台为什么拆 Agent、Grilling 和实现为什么分开、多阶段 Agent 有什么好处

技术上当然可以让一个 Agent 从头跑到底，问题是权限和上下文会混在一起。

需求澄清阶段只需要读代码，不应该有写权限；实现阶段需要写文件，但不应该自行决定需求已经确认；验证阶段应该依赖命令和浏览器证据，而不是复用实现者自己的结论。因此我没有为了数量硬拆很多“角色 Agent”，而是按责任拆 Thread 和阶段：Grilling 只读，Spec 和 Ticket 负责规划，实现 Thread 负责候选代码，验证由工作台宿主执行。

上下文也不是靠 Agent 记忆传递。稳定规则来自仓库文档，需求结论进入版本化 Spec，任务状态进入 Ticket，运行结果进入 Requirement，最终进入 Handoff。即使服务重启或换一段会话，也能从这些工程产物恢复。

如果一个大 Agent 在同一段上下文里又讨论需求、又写代码、又自我验收，它很容易把“我打算这样做”误当成“产品已经同意”，也容易因为前半段的错误假设继续向后执行。

## 智能产品研发工作台和 Cursor 这类编码工具有什么区别？

别名：工作台和 Cursor 有什么区别、工作台跟 Cursor 有什么区别、工作台和 Cursor 的边界、这是代码生成工具还是流程编排平台、为什么不直接用 Codex CLI、工作台是不是重复造编辑器

它更接近本地研发流程编排工具，Codex 是其中的执行引擎。

Cursor、Codex CLI 这类工具擅长理解和修改代码，但它们通常不知道：这次需求是否已经确认、哪些目录允许修改、哪条验收条件必须有证据、产品是否认可页面、前端是否同意合并。我的工作台处理的是这些跨阶段状态和权限。

比如 Agent 回复“改好了”，在普通对话里可能就结束了；在工作台里，这只代表一次 turn 完成。后面还要通过 Git 范围检查、typecheck、测试、build、真实路由检查和产品验收。任何必要检查失败，交付门禁都不会打开。

因此我不会重复造一个代码编辑器。底层模型和编码工具可以替换，工作台提供的是流程、边界和证据。

## 复杂业务里，智能产品研发工作台如何让 AI 理解项目上下文？

别名：AI 怎么理解历史业务、工作台如何提供项目规则、Agent 如何知道系统约束、分层上下文是怎么做的

我采用分层上下文，而不是把所有文档一次性塞进 Prompt。

`AGENTS.md` 放每次都重要、但模型猜不到的稳定规则，例如启动方式、可修改目录、必须执行的检查。模块 README 记录公共组件和业务模块的使用方式。每个需求的技术文档、Spec 和 Handoff 保留历史决策。重复流程写进 Skill，需要时才读取。

这套仓库内文档就是我们的项目知识库。它的好处是和代码一起版本管理，能通过 Git 找到当时的实现与规则，不依赖聊天记录。

比如后台筛选统一使用 Ant Design Form 和 Table，请求统一走项目封装，表单统一使用 React Hook Form。这些如果不写下来，模型仅凭当前页面很容易手写三个受控状态，或者另起一套 fetch。规则进入项目文档后，Agent 的默认路径会和团队保持一致。

## PRD 要求“保持原有逻辑不变”时，Agent 如何查清现有行为？

别名：Agent 去哪里查原有逻辑、保持审批逻辑不变怎么验证、PRD 里的原有行为如何落到 Spec、代码和文档冲突时信哪个

这类话不是可执行要求，我会让 Agent 先查事实，再把查到的结果带回需求对齐。

它会从目标路由进入页面组件，继续追踪权限判断、接口调用、状态枚举、公共 hooks、相关测试和模块 README。必要时再查同一业务过去的 Spec 或技术文档。查完以后不能只说“我理解了”，而要把“原有逻辑”翻译成具体边界。

例如产品说“增加待审批入口，但保持审批逻辑不变”。Agent 查到入口只对 `canApprove` 为真的用户展示，点击后复用已有审批弹窗，后台管理页还有另一套入口。最终 Spec 应明确：只在 `/competition` 增加入口，继续复用 `canApprove` 和原弹窗，不修改权限函数、审批接口和后台页面。

如果代码和文档说法冲突，我把运行中的代码和接口契约视为当前事实，再让产品或维护者确认业务意图，而不是让模型自己选一个相信。

## 智能产品研发工作台如何组织 PRD 知识并避免上下文爆炸？

别名：工作台有没有 PRD 知识库、如何避免把所有文档塞进 Prompt、历史需求怎么检索、项目上下文太长怎么办

有，但不是单独采购一个向量数据库后把所有 PRD 全量灌进去。我们的知识库直接落在仓库：项目规则在 `AGENTS.md`，模块能力在 README，单次需求在版本化 Spec 和 Handoff，通用操作在 Skill。

检索也按需求逐层展开。先读取短入口规则，再根据目标路由和修改范围读取最近的模块文档；只有命中具体业务时，才查相关历史需求。这样上下文里保留的是当前决策需要的信息，而不是一整个项目的文档 dump。

比如只改 `/competition` 的空状态，Agent 没必要加载后台权限、支付和发布文档。它先定位路由对应模块，再读取这个目录的 README、相关组件和最近一次同类 Spec。这样既减少 token，也降低过期知识干扰判断的概率。

## Agent 如何判断应该新增、修改还是复用旧模块？

别名：AI 怎么决定是新建还是复用、工作台如何约束重复造轮子、Agent 修改前会先查现有组件吗、什么情况下应该新增适配层

不会让模型完全自由判断。实现前已经有三层约束：产品确认的修改范围、仓库的 `AGENTS.md` 和 Skill，以及只读探索得到的候选模块。

Agent 必须先搜索现有组件、hooks、接口封装和相似页面，再在方案里说明为什么复用、为什么修改，或者为什么确实需要新增。候选文件列表只是缩小搜索范围，不会直接替它做最终决定。进入实现后，Git 范围检查负责阻止它改到确认范围之外。

还是用审批入口举例。如果仓库已有 `ApprovalDialog` 和 `useApprovalPermission`，默认方案应该是复用，而不是新建 `CompetitionApprovalModal` 和第二套权限判断。只有现有组件的接口无法覆盖需求，并且修改它会影响其他调用方时，才考虑新增适配层。

当前还没有自动判断“这段代码本应复用某个组件”的质量门禁，这部分仍由工程 Review 兜底。工作台能保证它先查、说明理由、限制范围，但不会假装已经完全替代架构判断。

## 新需求和历史业务规则冲突时，智能产品研发工作台如何发现？

别名：需求和历史规则冲突怎么办、Agent 如何发现权限冲突、工作台如何防止新需求破坏旧行为、业务冲突在哪个阶段处理

冲突发现分三层。

第一层是 Grilling。Agent 查到现有行为后，会把会改变实现的冲突作为问题提出，而不是静默选择。第二层是 Spec Review，产品确认目标和边界，前端确认技术影响。第三层是验证，用现有测试和真实页面检查确认旧行为没有被破坏。

例如产品要求“所有人都显示审批按钮”，但代码和历史文档都说明只有审批角色可见。Agent 应该指出这不是普通 UI 调整，而是在改变权限规则，并询问是只调整入口文案，还是确实修改权限。只要这个决定没有确认，服务端就不允许进入实现。

如果冲突只在运行时才能发现，例如接口对无权限用户返回 403，那么真实账号或 Mock 场景的页面验证会把它暴露出来。AI 自检有用，但最后仍要靠结构化确认和外部证据。

## 智能产品研发工作台里的业务、项目、组件和规范知识分别解决什么问题？

别名：工作台知识库怎么分类、业务知识和项目知识有什么区别、组件知识解决什么问题、工程规范应该放在哪里

我按“它帮助 Agent 做什么决定”来划分。

- 业务知识说明为什么存在、状态如何流转、哪些规则不能破坏。例如审批状态和角色权限。
- 项目知识说明怎么运行、目录怎么组织、验证命令是什么。例如 `pnpm --filter front dev` 和目标健康地址。
- 组件知识说明已有能力和推荐用法。例如表格、表单、弹窗应该复用哪个封装。
- 接口知识来自接口契约，说明请求和响应字段，避免模型猜类型。
- 工程规范说明哪些目录不能动、提交前跑什么、README 何时必须同步。

这几类信息不应该全写进一个大文件。入口越长，Agent 越难找到真正约束。我的做法是短规则做索引，详细内容按目录和任务类型读取。

## 智能产品研发工作台如何防止项目知识过期？

别名：知识库会不会成为维护负担、项目文档怎么保持最新、README 和代码如何保持一致、Agent 修改公共模块时如何更新文档

会，所以维护责任必须和代码改动绑定，而不是靠定期想起来再整理。

公共模块和组件目录都有自己的 README。模型修改相关公共代码时，同一张 Ticket 和 Review checklist 会要求同步 README；接口类型由契约重新生成，不允许手改一份长期漂移的副本；需求规则进入 Spec 和 Handoff，跟候选提交一起保存。

例如给公共 `DataTable` 新增列配置能力，只改组件代码、不更新 README，就不能算这张 Ticket 完整交付。下一次 Agent 读取文档时，看到的接口和代码才是一致的。

目前系统没有自动证明“所有文档都没有过期”。能做的是把文档放到离代码最近的位置、把同步更新纳入变更范围，并在 Review 中检查。后续可以对 README 中的代码示例和导出 API 做静态校验，但这不应被说成已经实现。

## 智能产品研发工作台如何使用 AST 和目录遍历？

别名：AST 生成项目文档准确吗、目录遍历生成知识库靠谱吗、静态分析能否理解业务规则、AST 在工作台里负责什么

当前项目会扫描目录、路由和源码来找候选位置，但没有把“全仓 AST 自动生成知识库”当成已经落地的核心能力。

这是一个有意的取舍。AST 很适合提取组件名、导出符号、参数和调用关系，却无法可靠解释“这个字段为什么不能改”或者“这个旧组件为什么仍要保留”。如果把机器生成摘要直接当成业务事实，会产生一种看起来完整、其实没人负责的知识库。

我的方案是让静态分析生成索引和候选证据，真正的业务规则仍由维护者写在 README、Spec 或 ADR 里。比如 AST 可以告诉 Agent `ApprovalDialog` 被 12 个页面引用，但“修改关闭行为会影响审批回退流程”必须来自测试、文档或负责人确认。

## 智能产品研发工作台如何定位需求对应的路由、页面和组件？

别名：Agent 怎么找到需要修改的文件、工作台如何根据 URL 定位源码、需求关键词如何定位组件、DOM 点选定位源码做了吗

当前做法是先由产品给出目标页面，工作台在确认范围里结合路由片段、需求关键词和目录结构找候选文件。Agent 再打开路由组件，沿 import、子组件、hooks 和接口调用继续追踪。候选列表的作用是少走弯路，不是自动指定最终修改文件。

例如目标 URL 是 `/competition/42`，需求里出现“待审批”。系统会优先找到 competition 路由、详情页以及包含审批文案或状态枚举的文件。Agent 继续确认入口是否已存在、权限从哪里来、弹窗是否能复用，再把影响范围写进方案。

下一步更理想的交互是让产品在预览里直接点选 DOM，把选中元素的文本、结构、路由和源码位置加入 Agent 上下文。源码定位可以参考 `@hyperse/inspector` 或 `vite-plugin-react-click-to-component` 的构建期注入思路，但核心 Inspector 我会自己包一层：高亮层、`SelectedElement` 数据结构、跨源 iframe 的 `postMessage`、Zustand 选中态和 Prompt 注入。

现成库大多解决“点击 DOM 后打开 IDE”，不直接解决“跨源 iframe 把业务元素送进 Agent 对话”。React 19 下也不能依赖旧的 `_debugSource`，更适合在构建期加 `data-source` 或结合 source map。这个 Inspector 是明确的下一步，不是当前已经完成的能力。

## 智能产品研发工作台生成的技术方案会细到什么程度？

别名：工作台 Spec 写多细、技术方案会指定代码行吗、Spec 需要包含哪些内容、方案如何让新会话继续执行

会细到足以让另一段干净上下文继续执行，但不会把每一行代码提前写死。

Spec 记录目标、非目标、修改边界、验收条件和风险；Ticket 再写一个用户能观察到的交付结果、可能涉及的模块、依赖关系和验证方式。文件路径可以作为调查结论记录，但不是不可变命令，因为实现时可能发现更合适的复用点。

例如“增加待审批入口”这张票会写：入口只出现在 competition 详情页；复用现有权限 hook 和审批弹窗；不修改审批接口；无权限用户页面不变；用有权限和无权限两种状态验证。它不会规定必须在第 83 行增加一个 Button，因为这种细节应该由实现阶段根据现有结构决定。

## 智能产品研发工作台为什么在技术方案后还要拆 Ticket？

别名：为什么有 Spec 了还要拆票、Ticket 解决什么问题、为什么不把完整需求一次交给 Agent、拆票对失败恢复有什么用

一方面是为了分步执行，另一方面是为了让失败位置和交付结果可判断。

如果把“加入口、接接口、补空状态、改权限提示、跑验证”作为一个大任务交给 Agent，中途失败时很难判断哪些已经完成、哪些只写了一半，也很难安全重试。Ticket 把它切成用户可观察的结果，每张票有自己的状态和验收条件。

例如第一张票只完成入口与权限展示，第二张票接审批交互，第三张票处理异常状态并完成页面验证。第二张失败时，系统知道第一张已经完成，第三张还没开始，不需要让 Agent重新理解和重做整个需求。

Spec 始终是全局约束，Ticket 是执行切片，所以拆票不是把需求切碎以后丢掉整体背景。

## 智能产品研发工作台如何避免 Ticket 拆得太细导致整体不连贯？

别名：Ticket 太细会不会只有局部正确、Ticket 依赖怎么处理、blockedBy 是什么、为什么 Ticket 按用户结果而不是按文件拆

会，所以 Ticket 不能按文件拆，而要按用户能观察到的结果拆，并且每张票都继承同一个已确认 Spec。

当前 Ticket 有 `deliverable`、`acceptanceCriteria` 和 `blockedBy`。依赖只能指向前面已经存在的票，缺失依赖和向前引用会被拒绝，从输入上避免循环。确认后只有无依赖票进入 queued，其余保持 pending；前置票全部 completed 后才解锁。当前 Node executor 仍一次消费一票，Go 迁移的后续阶段才会增加有界多 Worker、独立 worktree 和整合策略。

例如“提交审批”依赖“入口与权限状态完成”，就写成第二张票 blocked by 第一张。第三张“错误提示和重试”再依赖第二张。即使每张票单独执行，Agent 仍然收到完整 Spec、之前已完成的结果和当前差异。

当前先把“依赖就绪”和“执行并发”拆开：DAG 决定哪些票可以 queued，Node executor 仍串行消费。这样先验证调度正确性，再在 Go 阶段用独立 worktree 和显式整合处理真正并行带来的冲突。

## 智能产品研发工作台是如何按 Ticket 增量开发和记录状态的？

别名：AI 是一次生成还是按 Ticket 开发、Ticket 执行状态怎么记录、服务重启后开发任务怎么继续、用户双击执行按钮会重复建分支吗

按 Ticket 依赖图增量开发；当前 Node executor 逐张消费已经就绪的队列。

每张票经历 pending、queued、active、completed 或 blocked 等状态。实现 Thread 会在同一 Requirement 内连续使用，所以它能看到前一张票的代码结果；但决定能否继续的不是聊天记忆，而是持久化的 Ticket 状态、Git 事实和验证结果。

服务重启也是一个典型场景。假设第二张票执行到一半，磁盘上还是 running，但进程和心跳已经消失。系统不会假装它仍在执行，也不会把整条需求清空，而是把当前票恢复成可重试的 blocked，保留第一张票、需求分支和 Thread ID。

每个副作用请求还带幂等键，用户双击按钮或浏览器重试时，不会重复建分支、重复启动执行或重复提交。

## 智能产品研发工作台用了哪些外部工具？

别名：工作台用了哪些 MCP、Codex app-server 在工作台里做什么、agent-browser 解决什么问题、为什么接口能力用 Skill 和 Apifox CLI

我不会为了显得复杂，把所有外部能力都叫 MCP。当前主链路接的是 Codex app-server、Git、宿主验证命令和 `agent-browser`。它们分别负责 Agent 生命周期、代码事实、工程检查和真实页面检查。

接口能力采用 Skill + Apifox CLI，不通过 MCP 批量搬运数据。Skill 规定查询、生成和校验步骤，CLI 提供结构化且可复现的输出。这样比在对话里多次查询更节省上下文，也更适合生成文件。

设计稿解析目前没有作为平台主能力。对这个 MVP，先把真实业务页面、现有组件规范和产品验收跑通，比同时接入设计工具更重要。

选择工具的原则不是“能接多少”，而是这个工具能否提供模型不应该猜的事实，以及结果能否被复现和验证。

## 智能产品研发工作台如何把接口文档变成 TypeScript 类型和 Mock 数据？

别名：接口文档怎么生成 TS 类型、Apifox CLI 如何生成接口代码、Mock 数据如何覆盖业务场景、接口契约变更后怎么同步

这部分我已经做成了 Skill + Apifox CLI 的固定流程。

Skill 先根据项目和分支读取目标接口定义，CLI 返回请求参数、响应结构、Schema 和枚举。生成器再产出 TypeScript 请求与响应类型，并通过项目已有请求封装接入，而不是让模型根据接口名猜字段。

Mock 也不只是用类型随机填值。Schema 负责字段形状，需求场景负责业务组合。例如审批列表的 `status` 虽然有 pending、approved、rejected 三个枚举，但本次页面至少要准备：有待审批数据、空列表、无权限、接口失败和长文案五种状态。这样 Mock 才能服务页面验收，而不是只让类型检查通过。

如果接口契约更新，重新执行同一 Skill 和 CLI 流程即可得到可比较的类型差异。目前这条接口准备链路已经跑通，下一步是把它更深地接入工作台，让 Ticket 可以直接引用生成的类型和场景数据；工作台的基础研发闭环并不依赖它才能运行。

## 智能产品研发工作台如何保证 UI 还原和真实页面效果？

别名：设计稿很大图层很乱怎么办、Agent 生成 UI 后如何验收、工作台如何检查长文本和窄屏、页面还原是否依赖 Figma 自动转代码

我不会把整份设计稿原始图层全部塞给模型，然后期待一次生成正确页面。

先用真实项目的组件库、页面密度、按钮层级和响应式规则搭业务骨架；再按区域提取设计信息，例如页面头部、筛选区、列表和弹窗。实现后必须回到真实路由，用固定 viewport 检查页面，而不是只比对 JSX。

例如列表页先确认 Table、Form、分页和空状态都复用项目组件，再检查长标题、无数据、加载中、错误态和窄屏。设计 review 可以指出按钮过抢、信息密度不一致或文本溢出，但最终是否修改仍由产品判断。

目前项目强项是“在真实页面中验证修改”，不是宣称已经解决任意 Figma 图层到高保真代码的自动转换。

## 智能产品研发工作台如何完成自动化质检和问题修复？

别名：工作台自动化质检怎么做、发现验证问题后如何返修、验证矩阵如何阻止错误交付、Agent 连续修复失败怎么办

验证分成机器检查、运行时检查和产品验收。

机器检查由宿主运行 typecheck、测试和 production build，记录命令、退出码、时间和日志。运行时模块启动真实项目、检查健康地址和目标路由。`agent-browser` 保存 viewport、Accessibility Tree、语义引用，以及新增 console error 和 page error。

每条验收条件只能标成 `verified`、`failed` 或 `not-run`。必要检查失败或没跑，服务端不会开放产品验收。

例如页面能打开，但点击审批后 console 出现未处理异常。运行时验证会记成 failed，并带上对应证据。工作台不会无限自动修复，而是追加或重试明确的 Ticket，让 Agent在同一分支和实现 Thread 中处理；完成后只重跑受影响检查和必要回归。连续失败或需要业务判断时，把决定交回人。

这样可以避免最危险的情况：Agent 改一次、测一次、继续自我解释，最后在没人确认根因时越改越远。

## 智能产品研发工作台如何衡量效果？

别名：工作台有哪些效果指标、如何证明研发工作台有价值、交付周期怎么统计、为什么不说效率提升百分之七十

我会把核心指标放在需求交付周期，而不是只看生成了多少行代码。

第一组是时间：从产品创建需求到第一次可运行预览、到产品验收、再到候选提交分别花多久。第二组是返工：需求澄清轮数、产品返修轮数、人工修改时间。第三组是质量：必要检查首次通过率、页面验收一次通过率、越界修改次数和验证失败类型。

工作台已经记录首次预览、验收时间、修改轮次和验证结果，这些可以形成后续基线。真实案例也留下 12 项 verified、68 个语义引用和零新增页面错误。

面试里我不会编一个“效率提升 70%”。更可信的说法是：以前前端需要先理解需求，再重新组织 Prompt 和验收；现在产品可以直接得到可运行候选，前端把时间集中在技术 Review 和生产决策。随着试点需求增加，再用同口径历史数据比较交付周期。

## 智能产品研发工作台当前的试点规模怎么样？

别名：工作台现在有多少用户、研发工作台推广规模、三人小组如何试点、这个项目已经全公司使用了吗

目前是在一个三人小组内试点：一个产品、一个前端、一个后端。它不是已经推广到全公司的成熟平台。

这个规模反而适合验证最关键的责任边界。产品是否能独立完成需求对齐和页面验收，前端拿到 Handoff 后是否能理解代码和风险，后端是否能从接口契约角度补充边界，这些问题在小组里就能暴露。

试点阶段我优先观察的不是注册人数，而是不同角色能不能基于同一份 Spec 和验证证据协作，以及前端是否减少了重复转述。

## 智能产品研发工作台为什么没有立刻推广到后端、测试和全栈？

别名：工作台为什么先做前端、为什么不直接支持全技术栈、接入后端需要补哪些能力、前端 MVP 为什么不能直接搬到后端

不是因为流程只能用于前端，而是风险和验证方式不同。

前端页面的候选结果可以在本地分支和真实路由里直观看到，产品也能参与验收。后端会涉及数据库迁移、数据兼容、权限、幂等和线上依赖，测试场景还涉及账号、环境和数据隔离。直接把前端 MVP 的权限模型搬过去是不负责任的。

推广前需要补对应适配层：后端要有迁移沙箱、接口契约测试和数据回滚策略；测试侧要有稳定 fixture、账号和环境管理；跨仓需求还要解决多个 commit 的一致性交付。

因此我的顺序是先把单仓前端闭环跑稳，再扩展验证器，而不是先做一个覆盖所有岗位、但每条链路都不可靠的平台。

## 智能产品研发工作台产品化后最核心的能力是什么？

别名：工作台产品化的核心能力、研发工作台的壁垒是什么、为什么说它是可审计的本地研发控制面、这个工作台最重要的价值是什么

不是 Prompt 市场，也不是再做一个聊天窗口，而是“可审计的本地研发控制面”。

它至少要有四个核心能力：第一，接入仓库后识别并由工程师确认运行规则；第二，把自然语言需求变成版本化 Spec 和可验收 Ticket；第三，在受控权限和 Git 隔离下执行；第四，用机器检查和真实页面证据形成可恢复、可追溯的交付。

理想状态下，工作台可以识别 lockfile、workspace、package scripts、路由和候选 URL，展示判断依据，让工程师确认一次后写入受信配置。之后产品只需要选页面、描述结果和确认边界。系统可以自动准备依赖、启动项目、构造页面状态、执行 Ticket 和验证，但 push、merge、部署和生产配置仍保留人工确认。

真正的壁垒不是绑定某个模型，而是团队规则、项目知识、执行边界和验证证据能否形成闭环。模型可以换，这套交付标准不能跟着模型一起漂移。

## 一套实际需求如何在智能产品研发工作台中从头跑到尾？

别名：工作台完整需求流程、一个需求怎么从创建到交付、用实例讲讲研发工作台、待审批入口需求是怎么跑的

假设产品说：“在 `/competition` 页面增加待审批入口，有权限的人能看到并打开现有审批弹窗，其他页面和权限逻辑不能变。”

1. 产品创建 Requirement，只填写目标页面和期望结果，不输入命令和代码方案。
2. Agent 只读仓库，发现已有权限 hook、审批弹窗和后台入口，于是追问这次是否只改前台详情页。
3. 产品确认后，系统保存共同理解：复用原权限和弹窗；只改 competition 前台；无权限用户和后台页面不变。
4. 系统生成 Spec v1，产品确认后拆成三张 Ticket：入口与权限展示、审批交互、异常状态与回归验证。
5. 第二张票通过 `blockedBy` 依赖第一张，第三张依赖第二张；只有依赖满足的票进入队列。
6. 工作台确认仓库干净，从记录的 base revision 创建独立需求分支。
7. Codex 读取 `AGENTS.md`、模块 README 和相关源码，在确认目录内逐票实现。每个 turn 后重新检查 Git 范围。
8. SSE 把 app-server 文字增量实时投影到 React Query；断线或 sequence 缺口时重新获取 Requirement 快照。
9. 宿主运行 typecheck、测试和 build；Runtime 启动项目；浏览器分别检查有权限、无权限和接口失败状态。
10. 产品在真实页面确认结果。工作台写入 Spec、Tickets、验证矩阵和 Handoff，生成候选提交，但不 push、不 merge。

这条链路最重要的不是“Agent 会写一个按钮”，而是每一步由谁决定、凭什么进入下一步、失败后从哪里恢复都可以解释。

## 智能产品研发工作台最容易被追问的技术点有哪些？

别名：工作台最核心的技术点、研发工作台技术追问、项目里哪些技术点最值得讲、面试官会怎么追问工作台

最容易被追问的是流式消息的三层正确性、服务端状态与客户端状态的分工，以及 EventSource 重连后的快照恢复。

## 智能产品研发工作台为什么要同时保留 SSE delta、累计全文和 completed 全文？

别名：为什么流式消息要保留三份文本、SSE delta 和 completed 全文有什么区别、累计全文是做什么的、流式对话怎么保证最终正确

它们解决的不是同一个问题。

SSE delta 负责低延迟展示。用户不需要等整个 turn 结束才看到内容。

累计全文是服务端快照。假设 seq 1、2、4 到了浏览器，seq 3 因断线丢失，EventSource 即使重新连接，也不会自动补回已经发过的事件，因为当前服务端没有持久化事件日志和 `Last-Event-ID` replay。前端发现 sequence 缺口后重新获取累计全文，才能恢复正确内容。

`item.completed` 是最终校准。上游在生成期间可能修订同一个 item，新的全文不一定是旧文本的前缀。如果继续把差异当 delta 追加，就会保留已经被替换的内容。completed 到达后，服务端用同一 item ID 的最终全文替换累计正文，确保终态与上游一致。

## 智能产品研发工作台为什么用 React Query 管理服务端状态，同时保留 Zustand？

别名：React Query 和 Zustand 如何分工、为什么不把 Agent 消息放在 Zustand、服务端状态为什么只有一份真相、SSE 消息如何更新 React Query

Requirement、Ticket、Agent 消息和验证结果来自服务端，必须支持刷新、断线恢复和多入口重新获取，因此统一放在 React Query 缓存。SSE 到来时也是更新同一份 query data，不再维护第二套“实时消息真相”。

Zustand 仍适合纯客户端状态，例如 Inspector 当前选中的 DOM、侧栏展开状态、临时筛选条件和尚未提交的交互草稿。它不是被删除，而是不再保存应该由服务端恢复的业务状态。

否则同一条消息一份在 React Query、一份在 Zustand，SSE、轮询和用户操作同时更新时，很容易出现一边 completed、另一边仍 pending。

## 智能产品研发工作台为什么在 EventSource 自动重连后仍然需要快照恢复？

别名：EventSource 重连为什么不会自动补消息、SSE 断线后怎么恢复、sequence 缺口怎么处理、为什么重连成功后还要 refetch

重连只说明传输通道重新建立，不代表缺失状态已经补齐。

假设服务端依次发送 seq 1、2、3、4，浏览器收到 1、2 后断线，3 已经发出但没收到，重连后从 4 继续。连接是正常的，但页面缺 seq 3。如果服务端没有按 SSE 标准发送持久化 `id:`、保存事件日志，并根据 `Last-Event-ID` 重放，EventSource 不知道该补什么。

当前方案检测到 2 后直接出现 4，就 refetch Requirement 的累计快照，然后从新的 revision 继续消费实时事件。未来如果实现持久化事件日志和 replay，可以减少 refetch，但仍需要快照处理日志过期、服务重启和客户端落后太久的情况。

## 介绍智能产品研发工作台时必须说清哪些边界？

别名：工作台面试口径边界、这个项目哪些能力还没做、介绍研发工作台时不能夸大什么、产品验收是否等于生产批准

- 当前是前端页面需求的小组试点，不说成全公司、多技术栈平台。
- 当前不会为陌生仓库自动安装依赖或直接猜启动命令；理想方案是检测后由工程师确认，再写入受信配置。
- 当前代码位置来自路由、关键词和源码探索；DOM 点选 Inspector 是下一步方案。
- 接口类型和 Mock 采用 Skill + Apifox CLI；不把它说成 MCP，也不把“已跑通的接口准备流程”说成已经覆盖了工作台所有阶段。
- 当前 Ticket 支持显式依赖、pending/queued 区分和依赖解锁；Node executor 尚未并行，不能说成已经完成多 Worker 与 worktree 整合。
- 当前有真实验证数据，但没有同口径历史基线，不编造提效百分比。
- 产品验收不等于生产批准；系统生成候选提交，前端仍决定重构、保留或丢弃。

## 如何总结智能产品研发工作台的价值？

别名：工作台项目总结、智能产品研发工作台的价值是什么、面试最后怎么收尾、你对 AI 研发的理解是什么

我对 AI 研发的理解不是让 AI 替人把所有事情做完，而是把它放进一套可控的研发系统里：事实让它查，决策由人确认，执行受权限约束，结果由外部证据证明，失败以后还可以恢复。

智能产品研发工作台的价值也不只是少写几行代码。它减少了产品、前端和 Agent 之间的重复翻译，并把原来依赖个人经验的需求对齐、任务拆分、代码执行和页面验收，变成了团队可以共同使用和审查的工程流程。
