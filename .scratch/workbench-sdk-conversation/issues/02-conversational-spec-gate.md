# 02 — 对话式 Spec 门禁

**What to build:** 用户确认共同理解后，在原有只读规划上下文中进入 `to-spec`。系统自动加载适配工作台约束的 Skill，把已经确认的对话与只读仓库事实整理为版本化本地 Spec，并在同一时间线中展示可展开的结构化卡片。用户通过对话提出修订，明确确认后才允许继续。

**Blocked by:** 01 — SDK 对话内核与真实 Grilling.

**Status:** completed

- [x] 本地 `to-spec` Skill 明确把“发布”定义为工作台本地版本化文件和对话 artifact，禁止创建外部 Issue 或调用远程 tracker。
- [x] “确认共同理解”只推进到 `to-spec`，不会同时生成 Tickets 或开放 Implement。
- [x] 每次 Spec Turn 都明确加载 `to-spec` Skill，并保持目标项目只读。
- [x] Spec 文件按 Requirement 和版本保存在工作台数据目录，未确认前不写目标项目。
- [x] 对话中的 Spec 卡展示问题、方案、用户故事、实现决定、测试决定和非目标，并能查看当前版本状态。
- [x] 用户通过 composer 请求修改会生成新版本；旧版本保留且标记为已失效，不静默覆盖。
- [x] 修改已确认的共同理解会失效全部下游 Spec/Tickets，并重新进入 `to-spec`。
- [x] 只有当前有效 Spec 可以被确认；重复确认幂等，过期版本和错误阶段的确认在服务端被拒绝。
- [x] SDK 失败、取消和刷新恢复不会丢失已生成版本或错误状态，并可重试当前 Spec Turn。
- [x] 服务端状态机、文件持久化和浏览器内 Spec 审阅/确认流程通过测试。
